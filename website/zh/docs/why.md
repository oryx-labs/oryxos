# 为什么要做 OryxOS

## 企业需要的是 Agent Harness OS，不是一堆孤立的 Agent

每家公司此刻都有该交给 AI 应用的活：有人手工汇总的日报、凌晨三点要分诊的告警、每天的 PR 摘要、被回答了一百遍的客户问题。模型与 Agent 框架早就准备好了——可在大多数公司，应用还停留在 demo。

为什么？四道门槛，没有一道是模型：

**定义一个 Agent 需要工程师。** 今天的主流路径是写代码——选框架、搭运行时、写胶水逻辑、做部署。最懂业务的人（运维、客服、HR、财务）能用一句话把活描述得清清楚楚，却完全没法交付一个 Agent。

**数据必须出门。** 云上的 Agent 平台解决基础设施问题的方式，是把你的数据一并拿走。对任何有数据驻留、网络边界、审计合规要求的公司，这条路走不通。

**它是个黑盒。** 一个能执行 Shell、写文件、调外部 API 的 Agent——做过什么没有记录、能做什么没有白名单、危险动作没人审批——企业不可能把它放进生产。

**做一个应用容易，运行一组业务应用很难。** 把一次 LLM 调用套进循环只是脚本。而让很多业务应用共享模型、Tool、MCP Server、身份、预算、生命周期与治理，是一个平台级问题，几乎没有人把这一层交给你。

## 我们的答案

OryxOS 以开源、自托管的 Agent Harness OS 回应这四道门槛：让企业在同一套运行底座上**构建、运行、治理并持续优化**自己的 AI 应用。

![自然语言 + Memory + Tool + MCP + Skill + 知识库 + Notify = 一个能干活的 Agent](/images/agent-formula-zh.svg)

- **用自然语言，不用代码。** 一句话——或一个 Markdown 目录——就定义一个 Agent。Runtime 提供 Memory、内置 Tool、MCP 连接器、Skill、通知和调度。定义一个 Agent 的成本趋近于零。
- **你的基础设施，你的数据。** 一个私有部署的二进制，跑在你自己的服务器或 K8s 上。没有托管服务、没有遥测、不锁云。
- **玻璃盒，不是黑盒。** 每次 Tool 调用和 LLM 调用从第一天起就写进审计表——调了什么、传了什么参数、返回了什么、花了多久。文件 / Shell / HTTP 全走沙箱白名单。治理是执行链路的一部分，不是补丁。
- **面向应用的共享 Runtime。** OryxOS 为多个企业应用共享 Agent 与 Task 语义、能力注册表、模型路由、成本优化、调度、管理和 API。持久恢复、审批、评测和更完整的 Control Plane 属于演进中能力。

**让每家公司都能构建和运行自己的 AI 应用，并拥有统一、可治理的底座。**

## Agent 团队是一种持续演进的应用形态

真实的活很少只需要一种技能。「调研市场、起草报告、找人核对数字、发给团队」——这是一个**团队**的活：拆解、并行、评审、交付。OryxOS 将其视为建立在共享 Task 与治理之上的演进用例，而不是当前产品定义的全部：

> **你用一句自然语言发布一个任务 → 底座把它拆解 → 组织一支 Agent 团队 → 多个 Agent 分工协作 → 交付一个结果。**

![一支 Agent 团队怎么交付一个任务](/images/agent-team-zh.svg)

业界已经证明这个范式可行（planner–worker–reviewer 班子、Agent 间协作协议）。OryxOS 正在建设让它真正可治理的运行语义：行动可审计、策略与审批可拦截、成本按任务归集、迭代有界、Task 可恢复。见[路线图](./roadmap)。

## 为什么是 OS，而不是又一个框架

常见的误判是：更好的 Agent 需要更好的模型。生产环境里，瓶颈在 **harness**——模型和现实世界之间的那层脚手架：每次调用前组装对的上下文、工具走白名单而不是敞开、执行被隔离且可审计、消息可靠送达。

框架给你的是你自己代码里的一套 harness；OryxOS 把 harness 做成**基础设施**，让多个应用共享。这改变的是「谁能用」：有框架，是工程师造 Agent；有 OS，**每个能把活说清楚的人**都能参与交付企业 AI 应用。

## OryxOS 提供怎样的底座

**私有部署的执行环境。** OryxOS 运行在企业自己的基础设施中，让数据和运行过程留在企业边界内。

**可复用的应用 Runtime。** OryxOS 为多个应用和 Agent 提供共享 Harness：运行时生命周期、能力注册表，以及稳定的企业系统接入接口。

**可控的执行内核。** ReAct Loop 自实现且可检查，Provider 路由显式，执行与持久化都在 OryxOS 的控制范围内。

**在公开演进的平台。** 当前可用的是单节点 Runtime Kernel——Agent 定义、模型 Provider、Memory、Knowledge、Tool、MCP、调度、沙箱控制、审计记录、REST API 和 Web Manager。持久 Task 恢复、审批流程、模型路由与成本运营、分布式 Runtime，以及受治理的多 Agent 团队仍在持续演进。

## 为什么是现在

**AI 编程改变了成本结构。** 一个专注的小团队现在能构建和维护过去需要一个工程组织才能做的系统——OryxOS 自己就是这么造出来的：用 AI，由为结果负责的贡献者。

**开放标准刚好成熟。** MCP 已成为工具互操作的事实标准，A2A 正在成为跨 Agent 协作的标准。OryxOS 从第一天就构建在两者之上——接进 OryxOS 的东西在更大的生态里同样可用，反之亦然。

**真正的价值在运行一致性。** 当每个应用各自拼 Prompt、工具调度、审计和成本处理，生产问题就会变成每个应用各自的排查。共享 Runtime 通过明确的契约、持久审计和清晰的扩展模型，把这些能力做成一次建设、多个应用复用的企业资产。
