# 为什么需要 OryxOS

## Agent 能回答问题之后，难题才刚刚开始

把模型接到 Prompt 和几个 Tool 上，已经越来越容易。难的是让 Agent 真正在企业里做事：读取内部知识、操作企业系统、受预算约束、证明它做了什么，并且让一次应用的经验能复用到下一个应用。

这部分不应该由每个应用重复建设，它应该成为共享的 Harness。

## 企业真正需要控制什么

企业 AI 应用需要的不只是一个能力强的模型：

- **上下文**：正确的业务知识、实时数据与任务历史；
- **环境**：可以安全执行工作、连接企业系统的受控环境；
- **能力**：可扩展的模型、Tool、MCP Server、Skill 与凭证，而不是无限开放的调用权；
- **治理**：身份、授权、策略、审批、沙箱、审计与成本边界；
- **证据与学习**：交付物、验收证据、Trace、评测与反馈。

如果每个团队都各自实现这些东西，企业得到的只是一批 Demo 和脚本：规则会漂移，成本看不清，某个应用发生的问题也无法转化为下一个应用的改进。

## OryxOS 把这一层做成共同底座

OryxOS 是这一层的开源、自托管 Agent Harness OS。团队专注业务应用，Runtime 则承接共同的执行路径：Task 生命周期、受治理的能力调用、模型路由、成本归集、审计与运行运营。

它要解决的不是替代最强的 Agent，而是让任何 Agent 都能在企业环境中可用，同时企业仍然掌握数据、工具和运行规则的控制权。

## 同一个底座，可以构建不同的 Harness

业务能力不应该写死在内核中，因此同一套 OS 可以承载不同应用：

| 应用 Harness | 在 OryxOS 之上增加什么 |
| --- | --- |
| 研发 | 代码仓库、Code Agent、CI、代码评审与测试证据 |
| 客服 | 知识库、CRM、工单、审批与人工接管 |
| 运维 | Runbook、可观测性、受控操作与故障证据 |

OryxOS 提供它们共同需要的 Runtime 与治理语义；每个 Harness 负责自己的业务流程和验收标准。

## 方向

当前 Runtime 是起点，不是终点。OryxOS 正在公开演进持久 Task、恢复、审批、策略、模型路由、成本运营、评测与分布式执行。

方向很明确：企业应能构建自己的 AI 应用，接入最合适的 Agent，并让每一次有实际影响的 AI 行动都运行在同一套可扩展的底座上。
