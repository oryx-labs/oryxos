## 原则

1. **直连官方（OS 默认）**：`oryxos-channel-*` ↔ 平台开放 API / Webhook / TMC。自称 Agent OS，渠道面应是一等公民能力，不把「某云客服 / 聚合插件已支持」当成唯一入站路径。  
2. **成熟才接**：权限可申请 + 文档稳定 + 可验签/鉴权 + **能钉死一条上下行**。  
3. **会话窗 fail-loud**：有 24h/48h/条数限制就硬拒绝。  
4. **投诉 / 订单推送 ≠ IM**：物流、催单、交易投诉可另做 notify/工具，不标「客服渠道完成」。  
5. **一场景可多产品**：同一厂商多个面（例：企微应用机器人 vs 微信客服 vs 服务号客服）分列，避免混接。  
6. **第三方聚合 = 可选加速，不替代直连**：同事若主张「插件/工具已支持就先接」，可作 **可选适配器 / 过渡**（缩短有资质前的空窗），但：  
   - 不得挡住对应平台的官方直连排期；  
   - 不得成为该渠道在 OS 里的「完成定义」；  
   - 聚合层故障、限流、合同到期不能变成 OS 不可用。

## §D 本地生活 / 外卖

| ID | 渠道 | 开放平台常见能力 | 是否算「客服 IM」 | 成熟度 | 建议 |
|----|------|------------------|------------------|--------|------|
| L1 | 美团外卖等 | 订单/催单/配送状态推送、商家 API | 多为**业务事件**，不是聊天会话 | 🔍 | 订单类可做 **notify/工具**；会话式客服须单独找到官方 IM 再进渠道表 |
| L2 | 饿了么 | 同上，OpenAPI + 统一推送 | 同上 | 🔍 | 同 L1 |

**结论（调研阶段）**：外卖「企业刚需」首先是**订单与履约消息**；若你要的是「用户在 App 里跟店客服聊天由 Agent 接管」，必须再找各平台**会话/IM 产品文档**，不能拿订单 webhook 充数。
