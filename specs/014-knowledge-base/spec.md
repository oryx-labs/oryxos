## 1. 背景与目标

### 为什么做

OryxOS 的产品主张是一个公式：**自然语言 + Memory + Tool + MCP + Skill + 知识库 + Notify = 一个 Agent**。其中知识库是目前唯一完全缺失的要素。

没有知识库的 Agent 只能靠模型的通用知识回答问题——它不认识企业自己的运维手册、产品 FAQ、规章制度。后果是两个：企业最核心的「用自己的知识武装 Agent」场景无法交付；对比 Dify、RAGFlow、Coze 等以知识库为核心卖点的竞品，OryxOS 在客户评估中直接缺一条腿。

### 这个特性是什么（一句话）

让管理员把企业文档变成命名的「知识库」，Agent 关联之后就能在对话中检索这些知识并给出可核实的出处；知识库的操作方式由底座统一定义，具体实现（内置的或企业已有的外部 RAG 平台）以插件挂载。

### 做成了长什么样（三个画面）

1. 业务人员问 Agent「服务器磁盘告警怎么处理」，Agent 答出运维手册里的处置步骤，并注明来自 `[运维手册] disk-alert.md #第3段`；
2. 管理员在 Web 管理台五分钟内完成建库、传文档、绑定 Agent，全程不碰命令行；
3. 管理员在看板上发现「上周有 14 个提问没命中任何知识」，据此知道该补哪些文档。

## 2. 术语表

| 术语                      | 定义                                                                                |
| ----------------------- | --------------------------------------------------------------------------------- |
| **知识库（Knowledge Base）** | 一组企业文档的命名集合，如「运维手册」「产品 FAQ」。物理形态是工作区里的一个目录。                                       |
| **片段（Chunk）**           | 文档切分后的最小检索单元。检索命中的是片段，不是整篇文档。                                                     |
| **切分（Chunking）**        | 把一篇文档按结构（标题、段落）拆成若干片段的过程。                                                         |
| **向量化（Embedding）**      | 调用模型把文本转成数值向量，使「语义相近」可以被计算。需要模型服务（复用系统已配置的 Provider）。                             |
| **召回 / 融合 / 精排**        | 检索的三个阶段：先并行多路找候选（召回），再把多路结果按名次合成一个排序（融合），最后可选地用更强的模型重新精确排序（精排）。                   |
| **出处（Citation）**        | 每条检索结果附带的来源信息：知识库名 + 文件路径 + 片段位置，用于人工核实。                                          |
| **绑定（Binding）**         | Agent 与知识库的关联关系。一个 Agent 可绑多个库，一个库可被多个 Agent 绑。技术形态为文件系统软连接（符号链接），与 Skill 绑定同一机制。 |
| **后端插件（Backend）**       | 承载知识库实际能力的实现。内置本地后端把文档存在本机并自建索引；远程后端把检索代理到企业已有的 RAG 平台（RAGFlow、Dify、百炼等）。         |
| **能力声明（Capabilities）**  | 每个后端插件声明自己支持哪些操作：检索是必选项，管理操作（上传、重建等）逐项可选。界面据此决定显示哪些按钮。                            |
| **mock provider**       | 系统内置的假模型服务：不联网、无需密钥、同样输入恒得同样输出。用于无凭证环境的演示与自动化测试。                                  |
| **渐进披露**                | 只把知识库的名称与描述放进 Agent 的常驻上下文，正文内容在需要时才检索——避免撑爆模型上下文窗口。                              |
| **热加载**                 | 服务运行中检测到工作区目录变化（新增/修改/删除）后自动生效，无需重启。                                              |

**需求用语约定**：MUST = 必须满足（验收硬条件）；MUST NOT = 必须禁止。FR/US/SC 编号是稳定标识符，一经分配不因排版调整而变，编号不连续属正常。

| 新增权限模型                    | 沿用现状（可选 Basic Auth / 内网假设）      | 随平台 RBAC 特性统一处理                |

## Clarifications

### Session 2026-08-18

- Q: 重建索引期间的可用性策略（双缓冲 / 原地重建报不可用 / 原地重建关键词降级）？ → A: 双缓冲——旧索引持续服务，新索引后台构建完成后原子切换；重建失败旧索引不受影响。
- Q: 多库聚合检索的 top-K 语义（融合后总 K / 每库 K 合并 / 总 K+每库保底）？ → A: 融合后总 top-K——跨库排序取全局前 K 条，结果数与绑定库数无关。
- Q: 文档导入/索引的执行模型（两段式 / 全同步阻塞 / 全异步）？ → A: 两段式——上传同步完成落盘与解析校验（格式错误立即拒绝），切分与向量化由后台虚拟线程推进，文档状态可查（待索引→索引中→就绪/失败）。

## User Scenarios & Testing *(mandatory)*

### 角色与可见界面

四类用户、五个界面。每个用户故事标注其角色。

| 角色           | 是谁                             | 主要界面                          |
| ------------ | ------------------------------ | ----------------------------- |
| **终端用户**     | 通过对话使用 Agent 的业务人员；无需知道「知识库」概念 | 对话界面（CLI chat / REST / 未来 IM） |
| **知识管理员**    | 维护企业知识、配置 Agent 的运营/管理人员，非技术背景 | Web 管理台                       |
| **Agent 作者** | 用目录/Git 定义 Agent 的技术用户         | 文件系统、CLI、管理台                  |
| **集成开发者**    | 把底座接进业务系统的工程师                  | REST API                      |

各界面对知识库暴露什么：

1. **对话界面**：唯一暴露物是「带出处的回答」，出处格式统一为 `[知识库名] 文件路径 #片段位置`；
2. **Web 管理台**：知识库页（全生命周期 + 看板）、Agent 详情页（绑定管理）、新建 Agent 流程（关联入口）；
3. **文件系统**：`.oryxos/knowledge/<库名>/`（知识库实体）与 `.oryxos/agents/<Agent名>/knowledge/<库名>`（绑定链接），可纳入 Git；
4. **CLI**：`oryxos knowledge list`（与 `provider list` 等同族的查看命令）；
5. **REST API**：`/api/v1/knowledge` 全生命周期 + Agent 绑定端点。

### User Story 1 - 终端用户：提问得到有出处、可核实的回答（Priority: P1）

业务人员向 Agent 提问。问题涉及企业知识时，Agent 自主检索绑定的知识库、必要时读取原文补充，回答给出出处；问题无关时正常回答不受干扰。终端用户感知到的只是「这个 Agent 懂我们公司的东西，而且说得出依据」。

**Why this priority**: 这是知识库特性的全部对外价值；其余故事都是为让这一幕发生。

**Independent Test**: 手工构造知识库目录与绑定链接（不依赖管理台），通过 CLI chat 或 REST 对话验证。

**Acceptance Scenarios**:

1. **Given** 某 Agent 已绑定含相关文档的知识库，**When** 用户就文档覆盖的主题提问，**Then** Agent 检索命中、回答基于命中片段、并给出出处（知识库名 + 文件路径 + 片段位置）。
2. **Given** 检索命中的片段不足以回答，**When** Agent 按出处路径读取原文全文补充上下文，**Then** 读取成功（本地库文档在文件读取白名单内），回答被补全——片段是入口，原文是补充。
3. **Given** 同一 Agent，**When** 用户提问与知识库无关的问题，**Then** 正常回答；检索不命中时不编造出处、不中断对话。
4. **Given** Agent 绑定了多个知识库，**When** 检索，**Then** 默认在全部绑定库内聚合检索（结果按出处区分来自哪个库）；模型可通过工具参数限定单个库。
5. **Given** 未绑定任何知识库的 Agent，**Then** 其对话上下文零知识库注入；误调检索工具返回可读错误说明。
6. **Given** 任意一次检索调用，**Then** 与其他工具调用一样进入审计记录。

### User Story 2 - 知识管理员：在管理台完成知识库全生命周期（Priority: P1）

管理员在 Web 管理台：创建知识库（起名、写描述）→ 上传文档 → 看到切分与索引状态 → 在 Agent 详情页把库绑定给 Agent → 用对话验证效果 → 日常维护（增删文档、重建索引、改描述）→ 下线（删除，受引用保护）。全程不接触文件系统与命令行。

**Why this priority**: 让非技术人员独立闭环，是「最懂业务的人定义 Agent」主张在知识域的落地。

**Independent Test**: 仅通过管理台界面完成「建库 → 传文档 → 绑定 → 对话验证 → 删库」闭环。

**Acceptance Scenarios**:

1. **Given** 管理台知识库页，**When** 创建知识库并填写名称与描述，**Then** 工作区出现对应目录与清单；列表页展示名称、描述、后端类型、文档数、片段数、索引状态。
2. **Given** 一个知识库，**When** 上传一份文档（markdown/txt/文本型 PDF），**Then** 上传响应立即反馈格式校验结果（不支持类型/扫描件当场拒绝并提示）；文档状态从「待索引」推进到「就绪」，页面可见更新后的片段数与索引时间。
3. **Given** Agent 详情页，**When** 绑定/解绑某知识库，**Then** 即刻生效（下一轮对话上下文随之变化）；绑定视图与文件系统链接始终一致。
4. **Given** 一个仍被 Agent 引用的知识库，**When** 请求删除，**Then** 默认拒绝并列出引用它的 Agent。
5. **Given** 索引异常或向量化配置变更，**When** 触发「重建索引」，**Then** 全库重新切分向量化；重建期间旧索引持续服务检索，新索引就绪后原子切换（双缓冲）；重建失败时旧索引不受影响并显示失败原因。
6. **Given** 知识库页，**When** 查看某库详情，**Then** 可见文档清单（各文档的片段数与索引状态）并可单独删除文档。

### User Story 3 - Agent 作者：创建 Agent 时关联知识库（Priority: P2）

作者创建 Agent 的三条既有路径都能关联知识库：① 管理台新建表单中从已有知识库多选；② 「一句话生成 Agent」时，负责起草的模型知道当前有哪些知识库可用，生成的草稿可包含合适的绑定建议；③ 编辑既有 Agent 时增改绑定。

**Why this priority**: 关联入口若只存在于 Agent 建好之后的详情页，「一句话生成一个懂运维手册的助手」这条主打体验就断了。

**Independent Test**: 在已有知识库的前提下，分别走三条路径创建/修改 Agent，验证绑定生效。

**Acceptance Scenarios**:

1. **Given** 管理台新建 Agent 表单、系统中已有知识库，**When** 作者在表单中勾选知识库并提交，**Then** Agent 创建成功且绑定同步建立。
2. **Given** 「一句话生成 Agent」入口，**When** 输入的意图与某知识库描述相关（如「做一个答疑机器人，用产品 FAQ 库」），**Then** 生成的草稿包含该知识库的绑定建议，作者确认后生效；意图无关时草稿不含知识库绑定。
3. **Given** 既有 Agent 的编辑视图，**When** 增改知识库绑定，**Then** 与详情页绑定管理行为一致。

---

### User Story 4 - Agent 作者：GitOps 式声明与热加载（Priority: P2）

技术用户不碰管理台：把知识库目录（清单 + 文档）放进 `.oryxos/knowledge/`、建立绑定链接、全部纳入 Git 管理。运行中的服务自动发现、索引、生效；`oryxos knowledge list` 可查看全部知识库及其索引状态。

**Why this priority**: 与「丢目录即上线 Agent」同一心智模型；企业「配置即代码」的运维习惯。

**Independent Test**: 服务运行中，纯文件系统操作 + CLI 查看，完成知识库上线与绑定。

**Acceptance Scenarios**:

1. **Given** 服务运行中，**When** 向 `.oryxos/knowledge/` 放入一个合法知识库目录，**Then** 无需重启即被发现并索引，管理台与 CLI 均可见。
2. **Given** 已索引的知识库，**When** 其中文档被修改/删除，**Then** 索引在合理时间内自动更新，删除的内容不再被命中。
3. **Given** 放入不合法目录（缺清单/名称与目录不一致），**Then** 不注册、给出可读告警日志，不影响其他知识库。
4. **Given** CLI，**When** 执行 `oryxos knowledge list`，**Then** 输出各知识库的名称、描述、后端类型、文档数、片段数、索引状态。
5. **Given** 服务停止期间目录被修改，**When** 服务启动，**Then** 对账发现差异并重建受影响的索引。

---

### User Story 5 - 知识管理员：挂载企业已有的 RAG 平台（Priority: P3）

企业已在 RAGFlow/Dify/百炼等平台建好知识库。管理员创建一个「远程后端」知识库：目录内只有清单与连接引用（凭证走环境变量），绑定、检索、出处、审计与本地库完全同一路径；管理台按该后端声明的能力集渲染操作（只读库不出现上传/重建入口）。

**Why this priority**: 插件契约的价值证明。v1 交付契约与能力探测机制；具体远程适配器为后续特性。

**Independent Test**: 用一个测试用远程后端桩（声明仅检索能力）验证：绑定可用、检索带出处（或标注出处不可用）、管理台不渲染上传入口、误调管理操作在入口被可读拒绝。

**Acceptance Scenarios**:

1. **Given** 声明远程后端的知识库清单，**When** Agent 绑定并检索，**Then** 与本地库同一工具、同一出处契约（远程缺出处字段时明确标注「出处不可用」）、同一审计路径。
2. **Given** 该后端仅声明检索能力，**Then** 管理台对该库不渲染上传/重建入口；对其调用管理 REST 端点在入口返回「该知识库后端不支持此操作」。
3. **Given** 远程后端不可达，**When** 检索，**Then** 返回可读错误并入审计，不中断对话；管理台状态列显示不可用。

### User Story 6 - 集成开发者/CI：无凭证环境完整自测（Priority: P3）

开发者在没有任何真实 API Key 的环境（内置 mock provider 提供确定性向量）通过 REST 完整走通「建库 → 传文档 → 绑定 → 对话 → 命中带出处」，用于 CI、演示与验收；相同输入恒得相同结果，CI 可稳定断言。

**Acceptance Scenarios**:

1. **Given** 仅配置 mock provider 的环境，**When** 通过 REST 完成全流程，**Then** 各环节行为与真实 provider 一致且确定可重复。

### User Story 7 - 知识管理员：监控知识库使用效果（Priority: P2）

管理员在管理台看到每个知识库「被用得怎么样」：检索了多少次、多少查询没命中任何内容（零结果）、多少次发生了降级、哪些文档最常被命中、命中内容有多少真正被引用进了回答。据此判断知识库质量并决定补充哪些文档——无需查数据库或翻日志。

**Why this priority**: 「效果评估体系要跟上」是维护者明确的需求方向；没有观测，知识库上线后就是黑盒。v1 交付运营看板档（评测集回归与自动优化建议的去向见「范围」节）。

**Independent Test**: 对一个已被多次检索的知识库（含命中、零结果、降级三类调用），在管理台查看指标并与审计记录核对一致。

**Acceptance Scenarios**:

1. **Given** 某知识库已发生若干次检索，**When** 管理员打开该库详情的使用看板，**Then** 可见检索次数、零结果率、降级率、命中的文档分布、出处引用率，并可按时间范围过滤。
2. **Given** 存在零结果查询，**When** 查看零结果列表，**Then** 可见这些查询的原文（用于判断该补什么文档）。
3. **Given** 任一看板指标，**Then** 其数值可与审计记录核对一致（看板只消费审计数据，不另建统计路径）。

---

### Edge Cases

**权限与安全边界**

- 绑定/解绑是管理面动作（管理台、REST、文件系统持有者执行）；Agent 在对话运行时 MUST NOT 能通过任何工具改变自己的知识库绑定。
- 绑定链接指向知识库根之外、使用绝对路径、目标不存在、或名称与目标不一致：识别为非法绑定，拒绝生效并可巡检报告。

**外部依赖失效**

- 向量化服务不可用：导入/重建显式失败并可重试；检索自动降级为关键词检索并在结果中标注「降级」，对话不中断。
- 向量化模型或维度变更：系统识别不一致，阻止新旧向量混合比较并提示重建，不静默返回错误排序。
- 远程后端不可达：检索返回可读错误并入审计，不中断对话；管理台状态列显示不可用。

**输入异常**

- 空文档跳过；超大单文档（>10MB）拒绝并提示；二进制/不支持类型忽略并告警。
- 重名知识库创建：拒绝并提示。
- 中文与中英混排内容：切分与检索可用（语义路天然覆盖，关键词路按子串匹配）。

**多方交互**

- 多 Agent 绑定同一知识库：互不影响，检索结果一致。
- 多库命中同名文件：出处含库名，可区分。
- 对仅声明检索能力的库调用管理操作：入口即拒绝，不产生半完成状态。

## Requirements *(mandatory)*

### Functional Requirements

> 编号为稳定标识符，组内不连续属正常（历史编号不重排）。各组对应：A 实体与生命周期 → B 关联 → C 运行时使用 → D 契约与插件 → E 管理与观测 → F 效果评估。

**A. 知识库实体与生命周期**

- **FR-001**: 系统 MUST 以「一个目录 = 一个知识库」管理知识库实体：`.oryxos/knowledge/<库名>/` 内含清单文件（名称、描述、后端声明）与文档文件；工作区初始化 MUST 创建该根目录。
- **FR-003**: 文档（markdown / 纯文本 / 文本型 PDF）导入或变更后 MUST 自动切分为带位置信息的片段并向量化入索引；切分 MUST 不跨文档；出处位置 markdown/纯文本用片段序号，PDF 用页码。无文本层的扫描件 PDF MUST 在导入时被识别并拒绝、提示明确原因；文档解析 MUST 为本地后端内部的可扩展分层（后续增加格式不改契约）。
- **FR-010**: `.oryxos/knowledge/` 目录的增删改 MUST 被运行中的服务自动发现并触发索引更新（热加载）；服务启动时 MUST 对账目录与索引的差异。
- **FR-011**: 删除仍被 Agent 引用的知识库 MUST 默认拒绝，并返回引用它的 Agent 清单。
- **FR-014**: 系统 MUST 记录索引所用向量维度与模型标识；与当前配置不一致时 MUST 阻止新旧向量混合比较并提示重建。
- **FR-024**: 重建索引 MUST 采用双缓冲策略：旧索引在重建期间持续服务检索，新索引构建完成后原子切换；重建失败 MUST 不影响旧索引可用性并保留可读的失败原因。

**B. Agent 关联**

- **FR-002**: Agent 与知识库的绑定 MUST 以文件系统软连接为唯一事实来源：`.oryxos/agents/<Agent名>/knowledge/<库名>` 指向公共知识库目录的相对链接（与 Skill 绑定同一机制）；Agent 配置文件（frontmatter）中不声明知识库。绑定建立与巡检 MUST 校验链接真实指向仍位于知识库根目录内，拒绝绝对路径与越界链接。
- **FR-018**: Agent 创建与编辑的三条路径 MUST 均提供知识库关联入口：管理台新建/编辑表单可多选已有知识库；「一句话生成 Agent」的起草上下文 MUST 包含现有知识库名单（名称 + 描述，与工具/渠道候选同等待遇），生成草稿可含绑定建议且经作者确认后生效。
- **FR-019**: 绑定/解绑 MUST 仅为管理面动作（管理台、REST、文件系统）；MUST NOT 向 Agent 运行时暴露任何可改变自身绑定的工具。

**C. Agent 运行时使用**

- **FR-004**: 系统 MUST 提供内置检索工具 `retrieve_knowledge`：在发起 Agent 已绑定库范围内检索，返回 top-K 片段，每条 MUST 带出处（库名 + 文件相对路径 + 片段位置）。检索 MUST 遵循标准流水线分段：多路召回（语义 + 关键词并行）→ 融合排序（按名次融合）→ 精排（可选能力槽位）；内置本地后端 v1 实现前两段，声明精排能力的插件结果直通。
- **FR-005**: 每轮对话上下文 MUST 只注入绑定库的元数据（名称 + 描述 + 检索指引），MUST NOT 预载文档正文；未绑定任何库的 Agent MUST 零注入。
- **FR-012**: `retrieve_knowledge` 的每次调用 MUST 进入既有工具调用审计记录。
- **FR-013**: 向量化服务不可用时，检索 MUST 自动降级为关键词检索并在结果中标注降级状态；导入/重建 MUST 显式失败并可重试，MUST NOT 静默丢弃文档。
- **FR-017**: 本地后端知识库的文档目录 MUST 自动纳入文件读取白名单：检索命中后模型可按出处路径读取原文全文；远程后端命中无本地文件时 MUST 标注不可跟读，MUST NOT 返回不可用的路径。
- **FR-020**: 多库绑定时检索 MUST 默认聚合全部绑定库：跨库融合排序后取全局 top-K（结果条数与绑定库数无关），按出处区分来源；工具 MUST 提供可选参数限定单个知识库；限定不存在或未绑定的库时返回可读错误。

**D. 标准操作契约与插件**

- **FR-006**: 「知识」MUST 以底座级标准操作契约定义、知识库实现以插件挂载：检索为必选契约，管理操作（建库/删库/导入/重建/状态）为逐项可选能力——插件 MUST 显式声明能力集，对未声明能力的调用 MUST 在入口返回可读拒绝，MUST NOT 以运行时异常暴露。后端切换 MUST 不改变行为契约（同一套契约测试参数化覆盖各插件）。
- **FR-007**: 向量化的模型访问 MUST 复用系统现有 Provider 注册表按名引用（含凭证），MUST NOT 另建一套凭证配置；mock provider MUST 提供确定性向量（同一文本恒得同一向量）。
- **FR-015**: 知识库清单 MUST 可声明后端插件：默认为内置本地实现（零外部服务依赖）；声明远程后端的库目录内只存清单与连接引用（凭证走环境变量，不落明文），其绑定、披露、检索、审计 MUST 与本地库同一路径；出处契约对远程后端同样强制，映射不到时标注「出处不可用」。
- **FR-016**: 检索基建（向量化、索引存储、召回/融合/精排流水线）MUST 作为底座通用组件设计、不与「知识」语义耦合：记忆系统后续的语义检索升级 MUST 能复用同一套基建而无需重建。

**E. 管理与观测界面**

- **FR-008**: 系统 MUST 提供知识库 REST 端点：全局增删改查、文档上传与删除、索引状态查询、重建索引，以及 Agent 维度绑定三件套（列出/绑定/解绑）；响应遵循统一响应体。文档上传 MUST 为两段式：请求同步完成落盘与解析校验（不支持的格式/扫描件在响应中立即拒绝），切分与向量化由后台推进，文档索引状态（待索引 → 索引中 → 就绪 / 失败）可随时查询。
- **FR-009**: 管理台「知识库」页 MUST 落地：列表（名称、描述、后端类型、文档数、片段数、索引状态）、详情（文档清单与单文档操作）、创建/删除、上传、重建；Agent 详情页 MUST 可管理绑定；管理操作入口 MUST 按插件能力集渲染（不支持的操作不显示，而非点击后报错）。
- **FR-021**: CLI MUST 提供 `oryxos knowledge list`（与 `provider list` / `tool list` / `session list` 同族）：输出知识库名称、描述、后端类型、文档数、片段数、索引状态。

**F. 效果评估（运营看板档）**

- **FR-022**: 每次检索 MUST 记录命中明细（每条命中的库/文档/片段与相关性分数）与检索元信息（查询原文、耗时、零结果标记、降级标记），随既有工具审计落库；该埋点数据结构 MUST 一次设计到位以支撑后续评测集回归与优化建议特性直接消费，MUST NOT 需要二次埋点。
- **FR-023**: 管理台 MUST 提供按知识库聚合的使用看板：检索次数、零结果率、降级率、命中文档分布、出处引用率（命中出处出现在最终回答中的比例），并可按时间范围过滤、可查看零结果查询原文列表；看板 MUST 只消费审计数据，不另建统计路径。

### Key Entities

- **知识库（KnowledgeBase）**: 命名的企业知识集合，对应一个工作区目录；属性：名称（目录名，唯一）、描述、后端声明、文档集合、索引状态、片段总数、最近索引时间。
- **知识文档（KnowledgeDocument）**: 库内一份源文件；属性：相对路径、内容指纹（变更检测）、片段数、索引状态（待索引 → 索引中 → 就绪 / 失败，失败含可读原因）。
- **知识片段（KnowledgeChunk）**: 检索最小单元；属性：所属文档、位置、文本、向量、出处信息。
- **Agent 知识绑定（AgentKnowledgeBinding）**: Agent 与库的多对多关系，事实来源为文件系统软连接；属性：Agent 名、库名、链接合法性状态。
- **知识后端插件（KnowledgeBackend）**: 标准操作的实现单元；属性：名称、能力集声明（检索必备、管理逐项可选）、连接配置引用；内置本地后端恒可用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员从零建库、导入 10 份文档、绑定 Agent 到首次得到带出处回答，管理台路径 5 分钟内完成，全程零文件系统接触。
- **SC-002**: 万级片段规模下单次检索对用户无感知延迟（检索环节 1 秒内返回）。
- **SC-003**: 100% 检索命中携带完整出处并可回溯原文；本地库出处 100% 可被跟读。
- **SC-004**: 无真实 API Key 环境（mock）可完整走通 P1 场景且结果确定可重复（CI 稳定断言）。
- **SC-005**: 未绑定 Agent 上下文中知识库内容为零；误调检索 100% 得到可读错误。
- **SC-006**: 热加载：丢入合法目录 30 秒内可被命中；删除文档 30 秒内不再命中。
- **SC-007**: 三条关联路径（管理台、文件系统、REST）产生的绑定状态一致且在任一界面可见（管理台视图 = CLI 输出 = 文件系统事实）。
- **SC-008**: 「一句话生成」在意图与某知识库描述相关时，草稿给出正确的绑定建议（人工评审通过率 ≥ 80%）。
- **SC-009**: 管理员不查数据库、不翻日志，在管理台即可回答「这个库最近被检索多少次、多少查询没命中、该补什么文档」；看板指标与审计记录 100% 可核对一致。
- **SC-010**: 文本型 PDF 上传后可被检索命中且出处含页码、可回溯原文；扫描件 PDF 100% 在导入时被拒绝并给出明确提示。
- **SC-011**: 对仅声明检索能力的后端（远程桩验证）：管理操作 100% 在入口被可读拒绝、管理台 100% 不渲染对应入口；其检索结果与本地库走同一工具、同一出处契约、同一审计路径（三同可逐项核验）。

## Assumptions

以下为前提假设（区别于上表的已决策事项）——若某条不成立，需回到需求层重新评估：

- **规模假设**：单库万级片段、全站十万级以内；更大规模由可插拔后端（pgvector 等）承接，不在本特性验收范围。
- **单实例假设**：本特性在单实例部署下验收；多实例索引一致性随 v0.4 分布式底座处理。
- **切分默认值**：按文档结构（标题边界）优先、辅以长度上限；具体参数为实现细节，契约是「不跨文档、带位置、可回溯」。
- **检索默认值**：top-K 默认 5、可由工具入参覆盖；召回每路候选量与融合参数为实现细节。
- **向量化配置**：`knowledge` 配置段指定 provider 与模型；未配置时不静默回退（部分 provider 无 embedding 端点）——向量化按「不可用」处理：导入/重建给出可读配置指引报错，检索走关键词降级路（FR-013）；mock 需显式配置且恒可用。
- **权限现状**：沿用可选 Basic Auth / 内网假设；「绑定是管理动作」由界面归属表达（FR-019），非账号级权限。
- **宪法遵从**：跨模块契约上移 core、软连接真实路径校验、审计 day-one 落库、同步执行模型；新建模块的理由与模块表同步在 plan 阶段声明。
